Chantier « critères d'admission personnalisables » réalisé dans ce passage :

  `reponses_critere_candidature`), entités `CritereAdmissionPersonnalise`/
  `ReponseCritereCandidature`, CRUD complet côté responsable admission

  n'était appelée nulle part dans tout le code — le filtre automatique de
  présélection (TDR 3.1.1) était un champ de données inerte depuis le
  début, base et personnalisé confondus. Comblé par un nouvel endpoint
  `POST .../sessions/{id}/appliquer-filtre-criteres`, déclenché à la main
  par le responsable admission (voir LOG_BLOQUANT.md point 61 pour le
  raisonnement complet).
- **Frontend** : gestion des critères dans le drawer de session (espace
  responsable admission), champs dynamiques sur le formulaire de
  candidature (étape 2) selon le type du critère (texte, nombre, oui/non,
  choix).
- **Tests** : `SessionCandidatureCriteresTest` (aucune couverture
  n'existait avant pour `respecteCriteres`), `CandidatureServiceFiltreCriteresTest`,
  `SessionCandidatureServiceCriteresTest`, extension de
  `CandidatControllerSoumissionTest`. `mvn test -Dtest='inpg.sn.lms.recrutement.**'`
  et `npx tsc --noEmit -p tsconfig.app.json` passent tous les deux.
